# TikTokライバースカウト自動化 要件定義書（共有用）

## 1. この資料の目的

TikTok LIVE から候補ライバーを収集し、重複除外と必要な確認を行った上で、営業・確認作業につなげる全体像を共有するための資料。

この資料は共有向けであり、認証情報、APIキー、内部運用ルール、細かな判定条件は含めない。

## 2. やりたいこと

- TikTok LIVE 上の候補を日次で収集する
- 既存候補との重複を除外する
- 条件に応じて追加確認を行う
- 最終的に Google Sheets 上で候補管理できる状態にする

## 3. まず確認できていること

`agent-browser` を使って TikTok LIVE ページを確認し、候補収集の入口として使えるかを検証した。

ここでの `agent-browser` は検証用であり、本番の候補収集実装は `Playwright` を使う前提。

確認に使ったページ:

- `https://www.tiktok.com/@nozo.88y/live`

確認できたこと:

- `uniqueId` は URL と LIVE ページ内データの両方で確認できた
- `followerCount` は LIVE ページ内データから確認できた
- 実際に確認できた値
  - `uniqueId = nozo.88y`
  - `followerCount = 901`

この確認により、少なくとも `uniqueId` と `followerCount` については、画像判定ではなく LIVE ページの情報から取得する方針で進められる見込みが立っている。

## 4. 収集する主な項目

候補収集の段階で最低限持ちたい項目は以下。

- TikTokアカウントID
- プロフィールURL
- LIVE URL
- フォロワー数
- 配信タイトル
- 取得日時
- 配信画面のスクリーンショット

後続の確認結果として、必要に応じて追加したい項目は以下。

- 重複判定結果
- 一次判定結果
- 確認工程の結果
- どの運用パターンで処理したか

## 5. 全体フロー

全体の流れは以下。

1. TikTok LIVE から候補情報を取得する
2. 取得した候補を Google Sheets の既存データと照合する
3. 既存候補と重複しているものを除外する
4. 重複していない候補だけを次の確認工程に回す
5. 条件に応じて `Gemini API` または `Backstage` で判定・確認を行う
6. 最終候補を Google Sheets に集約して管理する

## 6. フローをもう少し具体的に書くと

### Step1. TikTok LIVE から候補を取る

Playwright で TikTok LIVE を巡回し、候補ライバーごとに以下を取得する。

- `uniqueId`
- `followerCount`
- `title`
- `live_url`
- `screenshot`
- `collected_at`

ここでの目的は、まず候補を漏れなく集めること。

### Step2. Google Sheets と照合する

取得した `uniqueId` を Google Sheets 上の既存候補と照合する。

ここでの目的は、すでに確認済み、または保存済みの候補を再処理しないこと。

### Step3. 重複でない候補だけ残す

重複している候補はこの段階で落とし、重複していない候補だけを次の工程に渡す。

この順番にする理由は、後ろの工程に進む件数を早い段階で減らせるから。

### Step4. `Gemini API` または `Backstage` で絞り込む

重複除外後の候補に対して、運用パターンに応じて `Gemini API` または `Backstage` を使って絞り込みを行う。

ここで分けて考えているのは、2つの役割が異なるため。

- `Gemini API`
  - スクリーンショットや配信情報をもとに、候補の一次判定を行う
  - 目的は、人が見る前に候補数を機械的に絞ること
- `Backstage`
  - 候補の所属可否など、営業判断に近い確認を行う
  - 目的は、営業対象にしてよいかを確認すること

この工程では「どちらを先に使うと全体効率がよいか」を比較したい。

### Step5. 最終結果を一覧管理する

通過した候補、途中で除外された候補、確認結果を Google Sheets に集約する。

これにより、誰が見ても「どこまで処理が進んだか」を追える状態にする。

## 7. 比較したい2つの運用パターン

### パターンA: 自動判定を先に行う

1. 重複除外後の候補に `Gemini API` で一次判定をかける
2. 通過した候補だけを `Backstage` の確認工程に回す

このパターンで `Gemini API` に任せる役割:

- スクリーンショットや配信情報をもとに、候補を自動で絞る
- 人が見る前のふるい分けを担当する

このパターンで `Backstage` が担当する役割:

- 自動判定後に残った候補について、営業対象として問題ないかを確認する
- 所属確認など、最終候補に近い判断を行う

このパターンの狙い:

- 自動で候補数を減らす
- 確認工程に回す件数を減らす
- 人手の負荷を下げる

### パターンB: 確認工程を先に行う

1. 重複除外後の候補を先に `Backstage` の確認工程へ回す
2. 通過した候補だけに `Gemini API` で一次判定をかける

このパターンで `Backstage` が先に入る理由:

- 営業対象として外れる候補を早めに落とせる可能性がある
- 後ろの自動判定に回す件数を減らせる可能性がある

このパターンで `Gemini API` が後になる理由:

- 確認工程を通過した候補だけに使うことで、API利用件数を抑えやすい
- 判定コストを下げながら運用できる可能性がある

このパターンの狙い:

- 判定コストを抑える
- 不要な候補を先に落とす
- どちらの順番が効率的かを比較できるようにする

## 8. 使用する主な仕組み

### TikTok LIVE

- 候補ライバーの収集元

### Playwright

- 本番の候補収集実装を担当する
- TikTok LIVE から必要情報を取得する
- 候補収集の入口を自動化する

### Google Sheets

- 候補一覧の保存
- 重複判定の基準データ管理
- 後続の確認結果の集約

### Gemini API

- 候補の一次判定を補助するために利用
- スクリーンショットや配信情報をもとに、候補を自動で絞る役割を持つ

### Backstage

- 一部候補の確認工程で利用
- 営業対象として問題ないかを確認する役割を持つ

### n8n

- 全体の実行順管理
- 外部連携
- 定期実行

## 9. 現在の実装優先順位

1. TikTok LIVE からの候補取得
2. Google Sheets での重複除外
3. 後続判定フローの比較
4. 定期実行と通知連携

## 10. 現時点の運用方針

- まずは安価な条件で候補を絞る
- 重複除外を早い段階で行う
- 判定コストが高い工程は後段に置く
- 確認結果は Google Sheets に集約する
- 候補収集の入口は、まず安定化を優先する
